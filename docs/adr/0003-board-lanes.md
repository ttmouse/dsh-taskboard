# 看板列从 7 条收敛为 5 条：列回答「该谁动」，状态保持 7 个

看板此前按 7 个状态各开一列。问题是列回答了一个人不问的问题（「这个任务叫什么状态」），
而不是人真正问的（「现在该谁动」）。用户的屏幕给出了证据：7 行里 4 行是空的，
而 5 件等他处理的事和 24 件已经结束的事占着同样的视觉权重。

我们决定把列与状态解耦：**状态仍然 7 个**（系统的词汇，精确、可查询、不动），
**列收敛成 5 条**（人的词汇，按「现在该谁动」分组）。

具体取舍：

- **「等你」= `in_review` + `blocked`**。这两个状态在机制上已经是同一件事：评论即执行的门控
  就是这两个状态（`DISPATCH_GATE_STATUSES`），也就是系统自己认定「球在人手上」的那两个。
  等外部回复（等第三方）也归这里——球仍在人手上，是你要去催。列内部按来源分段显示
  （待验收一段、被阻塞一段），避免「两种东西看不出区别」。
- **「待立项」不并入流程**。它与「等待认领」语义不同：待立项是候选（要不要做没拍板），
  等待认领是队列（定了要做，等机器）。自动承接只从 `todo` 挑（选择器），
  并进去会让人以为候选也会被自动跑掉。
- **空列不出现**，唯一例外是「等你」：它空着也留着，因为「没有等你的事」本身就是要看的信息，
  列消失会让人以为看板坏了。
- **终态降权**：「已完成」（`done` + `canceled`）默认折叠成一行计数，点开才铺开。
  终态不该和待办同权重。
- **删掉「显示空列」开关**。它存在的唯一理由是掩盖列太多；空列不再占位置之后它没有意义了。
  列的折叠开关由列自己承担（「已完成」「待立项」默认折叠，可手动展开；状态存 localStorage，按项目）。

## Considered Options

- **保留 7 列，只把空列藏起来**（原「显示空列」开关的做法）——否决：藏 ≠ 并。任务还在原地，
  人仍然得知道它藏在哪；「等你的事」散在两列里，扫一眼看不到全貌。
- **连状态一起合并成 4 个**——否决：状态是系统词汇，被门控、选择器、租约、API 各处引用，
  为界面好读去改它会牵连机制；而且 `in_review` 与 `blocked` 在流转规则上确实不同
  （一个走验收，一个走解阻塞）。
- **把「待立项」并进「等待认领」**——否决：见上，会让自动承接的边界在界面上消失。
- **用标签代替列**（同一列里用 tag 区分来源）——否决：位置比标签强。位置一扫就看到，
  标签要读。

## Consequences

- 新增 `web/src/boardColumns.ts` 作为列模型的唯一定义处（列 → 状态、出场条件、默认折叠）。
- `BoardColumn` 从「一个状态一列」改为「一条列收多个状态」，内部按状态分段；
  合并列的拖拽落点按落点位置判定（插在某张卡前面就沿用那张卡的状态，落在段尾沿用被拖卡片的状态）。
- `HiddenColumns`、`BoardSettingsMenu`、`IssueListView` 仍按状态工作，不受影响。
- 界面上的折叠态与显隐态存在 localStorage（`taskboard.laneCollapsed.v1`、`taskboard.laneVisibility.v1`），
  按项目区分。旧的两个键（`showEmptyColumns`、`columnVisibility`）废弃，不再读取。
- 失败轮次已经接进「等你」：一轮没跑完时，派发管线把失败写回议题
  （agent 署名的评论 + 移 `blocked`，见 `plugin/lib/index.mjs` 的 `reportRoundFailure`）。
  只写评论不建新状态：失败是**轮次的结果**，任务本身仍该人处理，所以它就是「等你」。
  移 `blocked` 前会重读一次最新状态，只在该议题仍是 `in_progress` 时移动——
  一轮如果先做了有意义的流转再死掉，不该被拖回去。
