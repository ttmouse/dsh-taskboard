# 任务驱动收敛为一条派发管线：评论即指令，按钮是不打字版，定时只是兜底

看板需要让人随时驱动 agent 推进某个议题，而定时认领（兜底巡场）无法满足「立刻、定向」。我们决定：不为新入口建新管线——评论即执行、干一轮按钮、定时认领全部收敛到同一条派发管线（给议题投一条指令 → 起一轮），差别只在入口与门控。

具体取舍：

- **不做 @ 智能体解析**。评论即执行已覆盖「对议题说话」；现阶段只有一个 agent 身份，@ 语法没有真实增量。等出现多个 agent 身份需要定向时再引入。
- **干一轮按钮全状态可用，评论派发维持 `in_review`/`blocked` 门控**。按钮是显式意图（点了就是要它干），评论是隐式指令（需要门控防误触发）。
- **轮次租约（数据库表）是运行状态的唯一依据**。它同时服务三个消费者：按钮的「Agent 进行中」显示、重复派发的互斥（409）、以及跨进程/跨驱动（按钮、评论）的一致判断。进程内的 `dispatchInFlight` 集合退化为快路径守卫。
- 已知边界：定时认领例程的跨宿主重复认领问题暂不在此租约内解决，属已记录的独立债务。

## Considered Options

- 给按钮建独立执行通道（复刻 AI 对话面板的轮次模型）——否决：两套轮次生命周期，成本与心智双份。
- @ 智能体语法（参照 Claude 的 @-tag）——否决：单 agent 身份下无增量，徒增解析规则与「评论算不算指令」的歧义。
- 仅把按钮接到定时例程「插队」——否决：延迟不可控，仍非立刻。

## Consequences

- 新增 `POST /api/tasks/:id/dispatch`（忙时 409）与 `GET /api/tasks/:id/dispatch`（进行中查询）。
- 零输入派发的提示词变体（`buildDispatchPrompt` 处理空评论）。
- 租约带 60 分钟过期（与认领执行器的单轮上限一致），防止宿主崩溃后议题被永久锁死。
