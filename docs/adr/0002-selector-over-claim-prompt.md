# 认领退役：选择进宿主，定时只是零输入派发

自动执行的原实现让 agent 在会话里「找到该项目最早的 todo 议题」再认领——把一个确定性判定外包给了模型：门控已经拉到完整待办列表却只留下计数，`/api/tasks` 的默认排序里根本没有「最早」，agent 每轮各自解释；同时定时认领绕开 ADR-0001 的派发管线自成一条执行路径，欠下跨宿主重复认领的租约债。我们决定：**选择是系统（插件宿主）的职责，agent 只承接被指派的议题**——定时认领改为「选择器挑出一个议题 → 走既有派发管线的零输入变体」，agent 自主找活的提示词路径整体删除，不做任何配置面。

具体取舍：

- **选择器是纯函数，永远不做配置**。资格 = `todo` + 未归档 + 无未完结的 blocks 入边；排序 = 优先级（urgent→none），同优先级按创建先后。「最早」降级为并列时的决胜规则。看板上优先级怎么摆，机器就怎么读——所见即所选，不暴露「排序策略」设置。
- **不给 agent 否决权**。系统说下一个是它就是它；选错修选择器（纯函数，坏得明明白白），不加「让模型再看看」的回退层。留退路等于保留两套语义。
- **一轮只做一个议题**。到点挑一个、派一轮，下个周期自然接上；单轮多议题让时长与评论排队语义失控。
- **例程 YAML 里的 prompt 退化为说明文字**。定时轮次实际由宿主派发，YAML 始终 `paused`，外部执行器跳过它；卡片文案描述机制，不再是指令。

## Considered Options

- 保留 agent 自主选活、仅把提示词写严——否决：确定性判定继续烧 token，「最早」依旧无定义。
- 宿主给候选清单、agent 保留否决——否决：机器做完判断再回头问，是选择责任不落地。
- 保留认领独立执行路径、仅预选议题 ID——否决：两套轮次生命周期并存，租约债照旧。

## Consequences

- `plugin/lib/claim-routines.mjs` 新增 `selectNextTask`（纯函数）与 `claimRoutinePromptText`，删除 `buildClaimPrompt` 的指令文案。
- `plugin/lib/index.mjs`：门控①从「数待办」改为「选择器出活」，返回 `{ automation, task }`；`executeProjectClaim` 删除，定时路径与「立即运行」按钮都收敛到 `runTaskDispatch` 的零输入变体——定时轮次自此进租约表，ADR-0001 记录的跨宿主重复认领债一并清掉。
- 零输入确认评论改为「已自动开始一轮」，对「干一轮」与定时选择同样成立。
- 界面无新配置、无新概念：项目开关照旧，「认领」一词从系统语义中退役（自动化页仅存卡片徽标）。
