# 忙碌时排队而不是丢活；租约只由持有者释放

两条相关的决定，一条是新增（排队），一条是纠错（租约归属）。放在一起写，因为
排队正好踩在租约上：如果不同时修租约，排队会顺着它变成空转。

## 一、忙碌时排队，而不是丢活

定时到点和自动化面板的播放按钮走同一条派发管线（ADR-0001）。管线在议题已有活轮次时
直接返回，于是：

- **定时**：那次触发白费，还要再等一个周期
- **播放按钮**：更糟——HTTP 早回了 202「已触发」，界面显示成功，**实际什么都没跑**

我们决定：**排队，等这一轮结束再跑**。每议题至多排一条，取走即消费。

具体取舍：

- **人类评论不排队**。评论会被在跑那一轮的队列读送达（`queuedCommentReader`，
  下一轮开始时投递）；再排一轮会把同一句话执行两遍。有评论载体的请求一律交给在跑那轮。
- **每议题至多一条，不叠加**。自动化反复触发不该把队列堆起来；先到的那条保留，
  重复请求仍然回 `queued`（这次请求确实被接住了），但不新增排队项。
- **排队要留痕**：写一条 `status: 'queued'` 运行记录，自动化面板看得见。
- **返回真实去向**，不再是布尔：`ran` / `failed` / `queued` / `skipped`。
  服务端的例程运行接口新增 `mode: "queued"`，界面照实说「已排队：这一轮跑完接着跑」。
- **排队那轮启动前重读议题**拿最新 version；重读失败就放弃这一轮并记日志，
  不抛错、不假装跑过。

## 二、租约只由持有者释放

`finally` 里原本无条件 `releaseDispatchLease`。一个因为「已有活轮次」而退出的派发，
会把**别人**的租约删掉——互斥随之消失。实测复现（真实数据库）：

```
轮 A 拿到租约: session-A
轮 B 想拿，应失败: null
此时租约属于: session-A | busy = true
未持有租约的一方 release 之后 -> busy = false，租约 = null
轮 C 于是也能拿到租约: session-C      ← 同一议题并排跑两轮
```

修法：用 `holdsLease` 标记，只有真正拿到租约的那一次才释放它。

**这条同时是排队的闸门**：没拿到租约的那次既不能释放，也不能去接排队的那一轮——
否则「排队 → 发现自己还是忙 → 再排队」会空转成死循环。

## Considered Options

- **忙碌时让请求等待（await 租约释放）**——否决：派发入口是 HTTP handler 或轮询回调，
  挂住它们会把请求/轮次拖满整轮（这个坑在本项目已经踩过一次）。
- **把排队的轮次也丢给定时器下次再挑**——否决：那是「下次再说」，不是「这次被接住了」；
  界面上仍然看不到这次请求的去向。
- **人类评论也排队**——否决：同一句话会执行两遍。
- **给租约加「持有者校验」再释放（release where session_id = ?）**——否决：治标；
  调用方本来就该知道自己有没有拿到，标记比校验简单且不依赖数据库往返。

## Consequences

- 新增 `plugin/lib/dispatch-queue.mjs`（排队语义的唯一定义处，可单独测）。
- `runTaskDispatch` 的返回值从布尔改为去向字符串；调用方按需判断。
- 例程运行接口的响应多一个 `mode: "queued"`。
- 测试：`plugin/tests/dispatch-queue.test.mjs`（队列硬性质）、
  `dispatch-queue-decision.test.mjs`（评论 vs 排队的分岔）、
  `dispatch-queue-resume.test.mjs`（取走即消费，钉住不空转）。
- 已知边界：排队表在内存里，宿主进程被杀则排队项丢失。这与租约的处境一致
  （进程没了租约也没了），且下一次定时/按钮会重新发起请求，故不引入持久化。
